# 验收测试（keel）

本目录是 spec 的第 3 层：用可执行的例子约束行为。单元测试跟着实现写在各模块里，不放在这里。

| 目录                | 内容                                                           | 预期值来源           | 谁负责                 |
| ------------------- | -------------------------------------------------------------- | -------------------- | ---------------------- |
| `rules/`            | 决策表：CSV 每行一组输入和预期结果，测试逐行执行               | 业务方或你给出的例子 | 人定，agent 写执行代码 |
| `properties/`       | 不变量：任何输入下都必须成立的规则，用属性测试生成输入         | 人写下的规则         | 人定，agent 写生成器   |
| `flows/`            | 状态机模型：动作、前置条件、状态变化，随机动作序列对比真实实现 | 人定义的模型         | 人定，agent 写测试     |
| `characterization/` | 给已有代码补的特征测试                                         | 当前实现的输出       | agent，可随实现调整    |
| `e2e/`              | 少量关键用户路径                                               | 人选定的路径         | agent 维护             |

写验收测试时：

- 预期值必须有独立来源：决策表、不变量、参照系统或人工推导。不能跑一遍实现再把输出填进去。
- `characterization/` 只描述现状，不是验收标准。把它当作验收依据之前，要先由人确认。
- 只测边界上的行为（公开入口、契约、可观察的状态），不测内部实现细节。
- mock 通过不等于真实集成通过；找不到入口或 import 失败，不算业务断言失败。
- 不变量不要写成“用另一种写法把实现再做一遍”。
- 修改 `rules/`、`properties/`、`flows/` 里已有的预期，必须单独提交并说明理由；这类改动需要人审核。
- 想确认测试真的有效时，故意改坏实现里的一行，看测试是否失败；核心模块可以运行
  `pwsh -File scripts/mutation.ps1`。
